# Panda 仿真与 ROS2 经验总结

按日期记录实践中的追问、解释和可复现的观察。工程实现与评估协议以 [README](README.md) 为准。

## 2026-11-06 物理步长与发布周期

**问：发布间隔不是物理步长的整数倍会怎样？**

以物理步长 2 ms、期望发布间隔 25 ms 为例，状态落在 0、2、4……ms，25 ms 不在物理步点上。可以按 25 ms 的发布节拍发送最近一次完成的状态并保留其真实采样时间戳，也可以在物理步完成时发布，使采样时刻为 26、50、76、100 ms 等，间隔在 24 ms 和 26 ms 间变化。具体选择取决于调度规则。

若墙钟每 25 ms 固定推进 12 步，仿真每次只前进 24 ms，两种时间会逐次拉开。本项目当前每个定时回调固定推进 10 个物理步，定时器周期由 `10 × model.opt.timestep` 得出；固定模型的 dt 是 2 ms，因此这一配置是整数倍。该节点没有实现任意发布周期的调度。见 [节点源码](ros2_ws/src/panda_sim/panda_sim/node.py)。

## 2026-11-07 ROS2 QoS 与命令行

**问：为什么话题有发布者，`reliable` 订阅却收不到，`best_effort` 订阅可以？**

发布者提供 `best_effort` 时，不能满足订阅者请求的 `reliable`。订阅者请求 `best_effort` 时，两者兼容。反过来，发布者提供 `reliable`、订阅者请求 `best_effort` 也兼容，因为订阅者接受较低的交付要求；对该订阅者不能据此承诺每条消息必达。

用户在 WSL 使用 `/w2_qos` 亲手验证：`ros2 topic info -v /w2_qos` 找到一个 `BEST_EFFORT` 发布者，`echo` 请求 `reliable` 时报告 `RELIABILITY` 不兼容，改为 `best_effort` 后收到 `data: hello`。查询时的 `Subscription count: 0` 只描述 `info` 执行当时的发现状态，后续 `echo` 才创建临时订阅者。

**问：这几条命令和参数是什么意思？**

`ros2 topic info -v <topic>` 查询话题、端点及其 QoS。`ros2 topic echo <topic>` 创建订阅者并打印收到的消息；`--qos-reliability` 设置订阅端可靠性，`--once` 收到一条后退出，`--timeout 3` 最多等待三秒。`ros2 topic pub -r 5 --qos-reliability best_effort /w2_qos std_msgs/msg/String '{data: "hello"}'` 以每秒 5 次发送指定类型的消息。终端中的行尾 `\` 是 Bash 续行符。

**问：QoS 有哪些策略，它们如何匹配？**

QoS profile 由多项策略组成。可靠性为 `best_effort` 或 `reliable`。持久性为 `volatile` 或 `transient_local`，前者只请求加入后的新消息，后者要求发布者能够保留历史消息；`transient_local` 发布者可匹配 `volatile` 订阅者，反向不兼容。两端影响匹配的策略均须兼容。

`history` 的 `keep_last` 和 `keep_all` 描述缓存方式，`depth` 指 `keep_last` 的条数。`deadline` 是对消息间隔的最大期望，发布端提供的期限须不大于订阅端请求的期限。`lifespan` 控制消息过期时间。`liveliness` 指活跃状态的维护方式，`lease duration` 是活跃租约期限。默认值可能取决于中间件，排障时应检查实际端点信息。见 [ROS2 官方 QoS 文档](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)。

项目的 `/clock` 发布使用 `best_effort`，轨迹命令使用 `reliable`。先检查话题、消息类型、域 ID 和 QoS，再根据运行日志判断回调是否执行和命令是否通过校验。见 [ROS2 通信复习卡](../../plan/12_复习卡片/02_ROS2构建与通信.md)。

## 2026-11-07 心跳超时与 reset

**问：补发心跳后 joint1 为什么没有变化？reset 为什么让 position 变化？**

用户先发送一条轨迹，心跳超时后日志显示保持最后目标，joint1 实测约 0.0645 rad。随后单独补发心跳，joint1 仍约 0.0645 rad，符合节点在超时后清除活动轨迹的逻辑。心跳只延长尚未过期的活动轨迹期限，不能恢复已结束的轨迹。

空闲时调用 `/panda/reset`，节点通过 `mj_resetDataKeyframe` 恢复 Panda 的 `home` 关键帧状态和控制输入，并重置仿真时间，再用 `mj_forward` 更新派生量。节点重建轨迹订阅以清理该订阅的积压，并清除心跳期限。执行中调用 reset 会被拒绝。

用户收到 `success=True, message='Reset to home'`，随后 joint1 实测约 -3.15e-10 rad，仿真时间从重置前的 23731.100003917 s 回退到 1.16 s。订阅到的这帧状态不是 reset 发生瞬间，节点已继续步进，因此其他关节可能偏离关键帧角度。该 reset 恢复仿真状态，期间没有执行从原姿态回到 home 的运动轨迹。代码见 [节点源码](ros2_ws/src/panda_sim/panda_sim/node.py)。

**问：正常执行后的 joint1 与心跳超时保持有什么区别？**

用户在超时场景测得 joint1 约 0.0645 rad。超时检查清除了活动轨迹，节点保持超时前最后写入的控制目标，关节状态随后趋近该目标。补发单独心跳后，实测位置仍约 0.0645 rad。

reset 后运行 C++ 固定轨迹发布器，用户测得 joint1 为 0.09999950448724192 rad，接近轨迹末点 0.1 rad。轨迹执行完成时节点保持末点目标；位置是动力学产生的反馈，控制目标与位置是不同的量。用户随后提供日志，确认本次输出 `Trajectory complete; holding final targets`，前一次输出 `Trajectory heartbeat timed out; holding last targets`。

轨迹正常执行中依赖心跳及时续期，单调时间超时后停止更新目标；正常完成则在仿真时间推进到末点后停止插值。两种情况下后续的 MuJoCo 物理步都会继续推进。

## 2026-11-07 rosbag2 播放器与仿真节点

**问：怎么从 topic info 找到发布者？rosbag2_player 是不是另一种仿真过程？**

用户关闭 Panda 仿真，循环播放 bag 中的状态和时钟。`ros2 topic info -v /panda/joint_states` 显示 `Publisher count: 1`、`Node name: rosbag2_player` 和 `Endpoint type: PUBLISHER`，随后读到 joint1 位置 0.0369831945 rad。发布者名称是该发布端点下的 Node name。

`rosbag2_player` 从 bag 读取先前录制的消息，并按回放时间调度重新发布选定话题。状态回放时，它发布过去保存的 `JointState` 和 `/clock`，本身不加载 Panda 模型或推进 MuJoCo。因此能检查录包中的状态消息能否被回放和消费，不能仅凭回放所得的曲线证明物理仿真可重复执行。`--loop` 会反复播放同一个包，仿真时间戳每轮会回到包开头。

若要检验命令重执行，从相同初态启动真实仿真节点，仅回放轨迹命令与心跳，令仿真节点产生新的状态和 `/clock`，并按轨迹接受后的仿真时间对齐比较。见 [录包回放协议](README.md#w5-正式节点录包与回放冒烟)。

## 2026-11-07 Bash 作业控制

**问：`jobs -l` 是什么意思？**

`jobs` 显示当前 Bash 终端管理的作业，`-l` 额外显示进程 ID（PID）。命令中间有空格。按 `Ctrl+Z` 会暂停前台作业，`jobs -l` 可显示其 `Stopped` 状态；`fg` 将最近一个作业恢复到前台，多个作业可用 `fg %1` 指定编号。`Ctrl+C` 向前台进程发送中断信号，常用于退出节点。`jobs` 只列出当前 shell 的作业，空输出不能证明其他终端没有节点运行，可用 `ros2 topic info -v /clock` 等命令检查 ROS 发布者。

## 2026-11-07 轨迹时间对齐与参考目标

**问：接受轨迹后 0.2 秒的参考目标怎样计算？**

固定轨迹的 joint1 目标从 0 rad 在 0.4 s 内线性变化到 0.1 rad。已执行 0.2 s 时，进度是 0.2 / 0.4 = 0.5，参考目标为 0 + 0.5 × (0.1 - 0) = 0.05 rad。该目标由轨迹插值得到；JointState.position 是 MuJoCo 动力学推进后的实际位置，二者可相减得到跟踪误差。

自动录包冒烟中，两次接受命令的仿真时间分别是 1.24 s 和 2.24 s。用户正确算出接受后 0.2 s 对应 1.44 s 和 2.44 s，应以各自相对接受时刻对齐。两次运行的完整状态对比及插值约定以 [README](README.md#w5-正式节点录包与回放冒烟) 和脚本为准。

## 2026-11-07 轨迹中的关节顺序

**问：为什么仿真节点内部顺序可能与 C++ 轨迹消息中的顺序不同？**

`JointTrajectory` 由发送方填写 `joint_names` 和每个点的 `positions`，位置通过对应下标绑定名称。Python 仿真节点独立定义内部臂轴顺序 `joint1` 到 `joint7`，并按名称查询 MuJoCo 关节地址及执行器映射。消息名称排列可与节点的内部顺序不同，只要名称与各点位置一致即可。

当前 C++ 示例和 Python 节点恰好都按 `joint1` 到 `joint7` 排列；倒序是此前功能检查过的另一种合法输入，不是当前 C++ 示例的实际排列。接收器核对七个不同的名称及点维度，再通过 `incoming_names.index(name)` 得到重排索引，将每个位置点转换为内部顺序。未知、缺失或重复关节名会被拒绝，执行器映射则通过模型传动关系验证。

**问：关节名错误时会输出什么拒绝日志？**

`trajectory_points` 检查消息的关节名称数量和名称集合。若 `joint1` 被替换成 `joint9`，检查会抛出 `ValueError("joint_names")`，接收回调捕获该异常并输出 `Rejected JointTrajectory: joint_names`。这是节点预期的日志格式；应在运行节点的终端查看实际日志。节点在该校验分支不会将该命令设为活动轨迹。

## 2026-11-07 Panda 与 MuJoCo 的关系

**问：Panda 和 MuJoCo 分别是什么，如何准确描述它们的关系？**

Franka Emika Panda 是机械臂；项目使用 MuJoCo Menagerie 提供的 Panda 仿真模型，模型文件描述关节、连杆、执行器和物理属性，scene.xml 是本项目加载入口。MuJoCo 是物理仿真引擎，加载模型后，`MjModel` 保存模型描述，`MjData` 保存某次仿真的可变状态、控制输入和仿真时间。

Python ROS2 节点按关节名检查并重排轨迹，在每个物理步前按仿真时间插值生成关节目标，写入 `data.ctrl`，再调用 `mujoco.mj_step(model, data)`。MuJoCo 根据模型与当前数据推进状态；节点从 `data.qpos`、`data.qvel` 按关节地址读取状态，构造并发布 `JointState`。插值在离散物理步上更新，实际位置受模型动力学和位置执行器影响。

Panda 的仿真模型与 MuJoCo 仿真引擎组成了本项目的仿真对象与执行环境，不代表接入了真实机械臂。参见 [节点源码](ros2_ws/src/panda_sim/panda_sim/node.py) 和 [README](README.md)。

## 2026-11-07 Panda 节点启动与暂停

**问：仿真机械臂启动后会复位，还是保留原来的位置？**

当前 `panda_sim` 每次新进程启动时创建新的 `MjData`，加载模型的 `home` 关键帧并调用 `mj_forward`，因此从 home 初始化，不继承退出前的仿真位置。启动后仍会继续步进，稍后读到的状态可能与关键帧存在动力学偏差。

如果只是用 `Ctrl+Z` 暂停同一个进程再用 `fg` 恢复，保留的是该进程暂停前的状态，后续行为仍受恢复后回调和心跳超时检查影响。调用 `/panda/reset` 则在空闲时将同一进程的仿真状态、控制量和时间恢复到 home。用户亲手验证了节点启动后的命令重执行与 reset。见 [节点源码](ros2_ws/src/panda_sim/panda_sim/node.py)。

## 2026-11-08 Panda 与强化学习策略接入

**问：原计划是否包含让强化学习策略读取 Panda 状态并输出动作？**

原 v5 计划将策略接入排除在范围外。现有项目已经验证的是固定轨迹到仿真状态、录包及回放。根据用户希望产出完整学习控制链路的目标，v6 计划增加 Panda 关节目标任务、SAC 训练、checkpoint 推理和 ROS2 执行与评估。

现有 ROS2 节点执行轨迹期间拒绝新轨迹，因此连续策略调用需要有命令完成反馈、状态新鲜度和心跳约定。两轴任务和状态动作定义、训练与部署一致性检查见 [工程主线验收](../../plan/11_工程主线验收.md)。截至本次规划，Panda 环境、策略训练和 ROS2 策略接入均待实现。

**问：没有真机，RTX 5060 Ti 16GB 能做具身学习吗？**

可先在仿真中做状态动作闭环和示范数据训练。LeRobot 硬件指南提供的粗略范围中，ACT 约 2–6 GB，SmolVLA 约 10–16 GB。显存占用还受模型、batch、图像和优化器影响；本机只确认 GPU 型号和 16311 MiB 显存，具体训练配置与耗时待实测。仿真验证和实机部署的证据应分别记录。

## 2026-11-08 提前学习 11 月 10 日正运动学

本人用简化例子计算绕竖直轴旋转。半径 0.4 m、转角 0.1 rad 时，末端高度不变，水平圆弧长为 0.04 m。取旋转前水平坐标 (0.4, 0) m，旋转后约为 (0.398, 0.040) m。

本人手动输入 `home` 关节角，FK 与 MuJoCo 的 `hand` 位置均约为 `(0.554499478, 0, 0.624502429) m`。在其他关节角保持不变时，将 `joint1` 设为 0.1 rad，两种方法均输出约 `(0.551729290, 0.055357577, 0.624502429) m`，脚本报告位置误差 `4.089e-16 m`，旋转矩阵元素最大绝对差 `2.554e-15`。上述精度比较是同模型内部的数值结果，个人画实际坐标变换链及解释姿态误差仍待完成。

**问：为什么 FK 命令给 joint4、joint6 等设置了非零角度？**

七轴 `home` 关节角来自固定模型的关键帧，依次为 `[0, 0, 0, -1.57079, 0, 1.57079, -0.7853]` rad。joint4 约为 −90°，joint5 为 0，joint6 约为 +90°，joint7 约为 −45°。本次比较两组姿态时保留 joint2 至 joint7 的 home 角度，只改变 joint1，便于观察第一轴运动的影响。joint4 的模型有效范围约为 `[-3.0718, -0.0698]` rad，0 rad 在此范围之外。离线 FK 脚本直接设置关节角并调用 `mj_forward` 计算位姿；动态运行中 `JointState.position` 是仿真推进后的实测状态，可以与保持目标有偏差。

**问：home 的非零关节角和物理机械臂的限位、碰撞有什么关系？**

关节限位约束各轴允许的角度，与关节机械结构和运动范围有关。home 是模型里预设的一组初始关节角，便于复位、复现和开始动作。home 的数值满足本项目的关节限位；是否发生自碰撞或与环境碰撞，还需结合连杆几何、环境、配置和运动路径单独验证。此次离线 FK 比较检查的是位姿计算的一致性。

**问：Panda 各关节是绕各自 XYZ 的哪个方向旋转？**

本项目固定的 Panda MJCF 中七个臂关节都是旋转关节，编译后每个关节在其局部坐标系的轴向均为 +Z。连杆之间的固定旋转使各关节局部 Z 在基座系中的方向不同。以 link0 为基座、home 关键帧为姿态，joint1 至 joint7 的正轴方向分别约为 +Z、+Y、+Z、−Y、+X、−Y、−Z。该表通过 MuJoCo 的关节世界轴转换到 link0 计算，仅代表 home 姿态；上游关节改变后下游轴的基座系方向也会改变。夹爪的 finger_joint1 和 finger_joint2 是平移关节。

**问：机械臂自由度多时，需要在脑海中想象完整姿态吗？**

**问：微小动作怎样区分控制作用与环境反馈误差？**

**问：FK 脚本做了什么，能否用重执行误差判断环境影响？**

重执行误差比较两次运行的实际状态，需固定或记录初态、环境、控制及对齐方式。它能反映给定条件下轨迹的重复性和已设置变化的总体影响；仅靠两次轨迹差无法识别单独原因，重复差小也无法证明模型准确或跟踪目标准确。更细分影响需要受控对照、测量定义和足够的重复。

**问：什么是 bootstrap，如何工作？** 用即时奖励加下一状态的价值估计构造当前价值的更新目标；以状态价值为简化例子，非终止时 `y = r + gamma * V(s')`。critic 根据目标与当前估计的差异更新；目标含模型估计，并非已观察到的完整未来回报。SAC 使用下一状态的策略动作、目标 critic 和熵项构造目标。本人的概括是利用 transition 与下一状态价值估计更新 critic。

**问：超时也当作终止会怎样？** 当前短检查中外部超时重置环境，但使用截断前真实的下一状态继续 bootstrap；任务终止则停止。把后续价值强制设零可能高估或低估：后续价值为负时可能高估，为正时可能低估。本人提出负奖励时可能高估；方向取决于整个后续价值，不能一概而论。本日为对话练习，未记录本人复跑 SAC smoke。

**问：为什么不先按 critic 的 -3 走多步，而要把估计向 -5.5 的目标调整？** `-3` 是当前 `Q(s,a)` 对累计回报的估计，不是机器人动作；环境由 actor 输出动作来推进，采样和 critic 更新可以交替进行，也可先积累更多数据。已有 transition 能构造一步 bootstrap 目标，因此不必等待多步或回合结束；多步目标也是可选方法。`-5.5` 是包含后续估计的训练目标，并非确定真值，梯度更新通常只让预测逐步靠近。本人正确指出 critic 向目标调整、actor 利用 critic 偏向高价值动作；SAC 还考虑熵。

**问：一步与多步 bootstrap 各有什么优缺点，SAC 为什么通常用一步？** 一步目标利用一条 transition 即可更新，适合 replay buffer 中的离策略数据，但更依赖下一状态价值估计，奖励传播可能较慢。n 步目标使用更多真实奖励，再从第 n 步估计后续价值，可能加快延迟奖励传播并减少对单次 bootstrap 估计的依赖，但等待连续片段、回报方差及截断处理更复杂。对于离策略 SAC，中间动作可能来自旧行为策略，多步目标需考虑策略不匹配、熵项和必要的校正；直接拼接并非总是无偏估计当前策略价值。一与多步不存在普遍优劣，标准 SAC 常用一步兼顾简单及 replay 兼容，也存在多步变体。此为原理讨论，未新增训练实验。

**问：不知道成功在多少步后出现，设定多步目标是否违背 off-policy？** n 是构造目标时最多纳入的连续步数，不是对成功时间的预测；片段中途终止即停止，外部截断时按任务语义使用截断前真实下一状态 bootstrap。离策略指学习目标策略可以不同于生成数据的行为策略，不是训练全程不需要环境；回放数据来自此前环境交互。多步经历的中间动作可能来自旧策略，需考虑与目标策略的偏差及校正；不校正的多步变体可以使用，但有偏差。一步目标奖励传播可能慢，但不能断言必然大幅偏离或无法纠正；多步增加序列存储、采样和计算成本，是否过大取决于 n 和实现。用户提出成功时间未知及离策略关系，已讨论上述区别。

**问：多步离策略中旧策略和当前策略不匹配带来什么偏差，如何校正？** n 步目标中间动作及其后续状态、奖励按行为策略生成，直接作为目标策略回报会评价混合策略而非严格的当前策略；偏差方向取决于行为，可能高估也可能低估。重要性采样按每步目标策略与行为策略的动作概率（连续动作为空间密度）之比重加权，需支持集覆盖与可得的行为概率，多步乘积方差可能很大。逐步重要性采样、截断权重与 Retrace/V-trace 等方法控制方差；简单截断或不校正可能产生偏差，具体目标及保证取决于算法。SAC 多步实现还需一致处理熵项、终止和截断；本节为原理讨论，未新增训练实验。
