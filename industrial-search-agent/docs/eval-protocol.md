# 评估协议

这份文档固定"怎么算分"，避免每次跑完再从代码里倒推口径。

## 1. 数据

- 题目：`data/questions/test_questions.json`，100 题，字段为 `id / question`。
- 标准答案：来自工作电脑上的政府文件，通过 `python -m eval.answers <文件>` 导入到
  `data/private/answers.json`。该目录已被 `.gitignore` 排除，不入库、不外传。
- 只有**同时有题目和标准答案**的题计入分母。缺答案的题会被单独报告，不当作 0 分。

## 2. 对比的四档检索

| mode | 含义 |
|------|------|
| `bm25` | 中文按字符切分的 BM25，模拟原有关键词 FAQ 系统 |
| `vector` | bge-small-zh 向量检索，RAG 基线 |
| `hybrid` | 两路召回各 Top-20，min-max 归一化后 0.6/0.4 加权融合 |
| `rerank` | 融合结果取 Top-20 送 bge-reranker-base 精排，取 Top-5 |

融合权重 0.6/0.4 与 Top-K 都是拍定值，不是调出来的。真要说"fusion 比单路好"，
需要先在验证集上扫权重——这件事没做，所以结论只到"融合不比单路差"。

## 3. 指标

- **命中率**：标准答案去掉停用字后的字符集合，有 ≥40% 出现在 Top-5 任一片段里，
  记该题命中。40% 是拍的阈值，不是标定值。
- **关键点覆盖率**：标准答案的字符有多少比例被 Top-5 覆盖，取值 [0,1]，按题平均。
  比命中率细一档，用来区分"沾到一点"和"基本覆盖"。
- **Top-1 命中率**：命中的片段里，有多少排在第 1 位。同一批答案都在 Top-5 里时，
  这条能区分"排得靠前"和"排在最后一位"。
- **MRR**：命中名次的倒数按题平均。没命中的题记 0。
- **延迟**：单题端到端耗时，含检索、不含首次模型加载（评估前对每档做一次预热）。

四档在同一批题上跑，命中率往往一起接近饱和（Top-5 里只要出现答案原文就算命中）；
真正拉开差距的是 Top-1 和 MRR，看表时以这两列为准。
- **相关性 / 拒答率**：只在 `--gen` 打开时计算，需要调用 GLM。

## 4. 默认不做什么

- **不调用外部 API**。语料是政府文件，检索片段发出去就等于外发内容。
  生成环节默认关闭，只算检索侧指标。
- **不做 LLM 判分**。LLM 判分需要把标准答案和回答一起发出去，同样受上面这条约束。
- **不报显著性**。100 题是一次性评估，没有重复运行，四档之间的差值没有方差估计；
  差距小于 3 个百分点的，只能当噪声看。

## 5. 已知局限

1. 字符级重叠对同义表述不敏感：答对了但换了说法，覆盖率会偏低。
2. 标准答案是从文件里摘的原文，检索片段也来自同一批文件，命中率天然偏高；
   这个指标衡量"能不能找到出处"，不衡量"回答对不对"。
3. 40% 的命中阈值没有标定，换语料可能要重调。
4. 单次评估，没有 seed、没有置信区间。

## 6. 与简历口径的对应

- 可以写：四档检索在同一批题上的命中率与覆盖率对比，以及各自延迟。
- 不可以写：回答准确率（需要人工或 LLM 判分，没做）。
- 不可以写：融合权重经过调优（没做）。
