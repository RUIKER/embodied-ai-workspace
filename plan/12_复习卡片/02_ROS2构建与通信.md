# ROS2 构建与通信

> C++ 发布、Python 接收和 Panda 状态发布已在 WSL 2 的 ROS2 Lyrical 上通过冒烟。见 [构建与复现](../../hands-on-reinforcement-learning/15_RobotSystem/README.md#ros2-端到端冒烟)。

## 1. 最小通路

```text
C++ rclcpp 发布器 → ROS2 topic → Python rclpy 订阅回调
                                      ↓
                              接收并记录消息
```

在兼容的 Ubuntu、ROS2 和 Python 组合上，先 `source` 对应 ROS2 环境。工作区用 `package.xml` 声明依赖，C++ 包用 CMake 声明目标与安装规则，Python 包提供节点入口。`colcon build` 成功后，在每个启动终端加载工作区 `install/setup.bash`，再运行节点。先记录一条实际收到的消息，之后再接入 MuJoCo 状态发布。版本与环境阻塞见 [工程验收](../11_工程主线验收.md)。

本项目中，`panda_sim/setup.py` 将 `panda_sim_node` 映射到 `panda_sim.node:main`。`panda_trajectory_cmd/CMakeLists.txt` 则把编译出的 `publish_trajectory` 安装到 `lib/panda_trajectory_cmd/`。用 `colcon list --base-paths <源码目录>` 检查构建前能否发现源码包，用 `ros2 pkg executables <包名>` 检查加载工作区后能否发现已安装的入口。两次检查分别覆盖源码布局和安装环境。

## 2. 看得见 topic 却收不到

1. 用 `ros2 node list`、`ros2 topic list -t` 检查节点、话题全名和消息类型。节点缺失时先查启动日志、环境与 `ROS_DOMAIN_ID`。
2. 用 `ros2 topic info -v <topic>` 对照两端 QoS。发布端提供 `best_effort` 时，要求 `reliable` 的订阅端无法匹配。轨迹命令按计划使用可靠传输，状态端单独选 QoS 并写入配置。
3. 用 `ros2 topic echo <topic>` 查看样本，用 `ros2 topic hz <topic>` 观察该诊断订阅端的接收频率。CLI 的 QoS 要与发布端兼容。CLI 收得到、应用没反应时，继续查 executor 是否在 spin、回调是否进入，以及校验日志。

可靠传输描述消息交付能力。执行端还要检查命令年龄，避免按过期命令行动。依据见 [ROS2 Humble QoS 文档源码](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)。

11/7 在 WSL Lyrical 实测：C++ `demo_nodes_cpp talker` 发送，Python `demo_nodes_py listener` 收到。另用 `ros2 topic pub -r 5 --qos-reliability best_effort /w2_qos std_msgs/msg/String '{data: "hello"}'` 发布，`topic info -v` 能看到发布者。`topic echo` 显式请求 `reliable` 时报告 `RELIABILITY` 不兼容，切到 `best_effort` 即收到 `data: hello`。正式节点运行时，可用 `ros2 topic info -v /clock` 查看它提供的可靠性策略。

## 3. 自测

- **改参数前先预测**。最小通信跑通后把发布周期翻倍，预测订阅端观测频率约减半，用 `topic hz` 和接收日志解释实际差异。
- **面试追问**。构建、发现、匹配、进入回调分别用哪条日志或命令证明？回调接入仿真后，谁拥有 MuJoCo 状态并负责推进？
